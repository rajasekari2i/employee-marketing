## Why sequential, not parallel, work units

Several work units below edit the same shared files (`apps/api/prisma/schema.prisma` in WU-01/WU-02; `apps/api/src/main.ts` in WU-01/WU-04/WU-07). The orchestrated-execution skill requires non-overlapping file scopes for parallel work units, so this plan runs WU-01 → WU-02 → WU-03 → WU-04 → WU-05 → WU-06 → WU-07 strictly in sequence. This is a deliberate, file-scope-driven decision, not under-parallelization for its own sake — it keeps every commit buildable on top of the last.

## On work-unit size vs. the "~5 files" guideline

The orchestrated-execution skill's pre-flight checklist guides toward "each work unit has a single responsibility (max ~5 files created/modified)." Four work units below exceed the file count — WU-01 (12 entries), WU-04 (11 entries), WU-05 (7 entries), WU-06 (6 entries) — and this is a deliberate, acknowledged choice, not an oversight:

- **WU-01** (monorepo scaffold): the 12 entries are six *new, empty projects/packages* (`apps/api`, `apps/mobile`, `packages/config`, `packages/shared`, plus workspace/turbo config and one `schema.prisma` stub line). There is no smaller grouping that doesn't either leave a project half-initialized at a checkpoint or create an artificial dependency between, say, `apps/api`'s `package.json` and `apps/mobile`'s `app.config.ts` — they are independent until WU-02+ start filling them in. Splitting this into 6 one-project WUs would add five extra IMPLEMENT→VALIDATE→REVIEW→COMMIT cycles for work that is not independently reviewable (an empty NestJS skeleton has nothing in it yet to adversarially check against a spec).
- **WU-04** (request pipeline): 11 entries, but each is a single small guard/pipe/filter/interceptor (most are 20–60 lines) that only has meaning as part of "every route in the app is now covered by this security/validation layer" — the DoD itself (item 10) *is* the cross-cutting integration check, so reviewing any one guard in isolation from the others would miss exactly the kind of gap this guideline exists to catch (a forgotten global registration). This WU is one responsibility — "the request pipeline is live" — expressed across many small files, not many responsibilities in one WU.
- **WU-05** (auth core): 7 entries are the single `auth` module's own internal layers (hashing utility, token service, controller, service, module file, the seed script that depends on it, and its one-line `app.module.ts` registration) — splitting the controller from its own service from its own module file would create sub-work-units with no independent DoD (a controller with no service does nothing).
- **WU-06** (files module): 6 entries, same reasoning as WU-05 — one module's own layers plus its registration line.

In every case, the excess is file *count* within one cohesive module, not scope beyond one responsibility — each WU still maps to exactly the task range stated (e.g. WU-04 = "the request pipeline exists and is wired in," entirely T022–T030) and none could be split without either stranding half-finished code at a checkpoint or reviewing a file in isolation from the other half of its own feature.

2a. **Non-superuser connection role (load-bearing for DoD item 2 above)**: Postgres RLS is bypassed entirely for superusers and (without `FORCE`) for table owners — `FORCE ROW LEVEL SECURITY` only forces it for the table's owner, not for every other role. Since the local dev setup previously connected as the `postgres` superuser, the migration must also create a plain, unprivileged, non-owner role (e.g. `app_user`) with ordinary CRUD grants, and `apps/api/.env`'s `DATABASE_URL` must switch to it — otherwise every policy in DoD item 2 would silently never apply. A separate `MIGRATE_DATABASE_URL` (superuser) is needed for schema/DDL changes, since `app_user` deliberately lacks those privileges.
2b. **`company_id IS NULL` rows (the System Admin's own `User` row, and any System-Admin-owned `FileObject`)**: in SQL, `NULL = anything` — including `NULL = NULL` — is never `TRUE`, so the policies in DoD item 2 must include an explicit escape for this case or that row becomes permanently unreadable/uninsertable under any `app.company_id` value, silently blocking the login and seed work this schema exists for (found during this work unit's own checkpoint review, not foreseen when the DoD was first written). The escape is a dedicated session flag, `app.is_system_context`, set only by code genuinely acting as the platform itself — verified live to not grant visibility into other tenants' real rows when set. Applies **identically** to both the `users` and `file_objects` policies (data-model.md: a `FileObject`'s `companyId` "matches the owning user's company," so it is nullable for the same reason `User.companyId` is) — a first pass at this fix only updated `users` and left `file_objects`'s policy comment claiming a parity it didn't have; both are now identical on purpose.

### WU-07: Observability + mobile skeleton

**Maps to**: tasks.md T040–T041 / GitHub issues #40–#41

**DoD**:
1. `pino` JSON logging in `apps/api/src/main.ts` with `requestId, companyId, userId, route, durationMs` fields and a redaction list covering `password, token, authorization, latitude, longitude, reasonText, otp` (T040)
2. `apps/mobile/src/navigation/RootNavigator.tsx` (role-based navigator stub reading `useSession().role`), `apps/mobile/src/lib/secureSession.ts` (`react-native-keychain`-backed getters/setters for the access/refresh pair), `apps/mobile/src/api/client.ts` (typed fetch client scaffold reading shapes from `packages/shared`) (T041)

**File scope**: `apps/api/src/main.ts` (pino section), `apps/mobile/src/navigation/RootNavigator.tsx`, `apps/mobile/src/lib/secureSession.ts`, `apps/mobile/src/api/client.ts`. **Amendment, written here after this work unit's own adversarial review**: also `apps/api/src/app.module.ts` (registering `nestjs-pino`'s `LoggerModule.forRoot(...)` — a necessary addition this DoD item cannot be achieved without, following the same "minimal, documented app.module.ts addition" pattern already established for `@Public()`/`@SkipTenant()`/every other module registration in this plan) and `apps/api/src/infra/logging/deep-redact.ts` (new). The redaction requirement was first implemented using pino's built-in `redact.paths` option (fast-redact) — live-verified by adversarial review to only match a fixed set of exact, literal paths (`req.body.password`, bare top-level `password`, etc.), leaving every OTHER nesting depth (e.g. `{ user: { credentials: { password } } }`) to log in plaintext, since fast-redact has no arbitrary-depth/recursive matching mode. This directly violated CLAUDE.md Constitution rule 9's blanket "no secret/token/password/coordinate/reason in any log line" — not a hedged or best-effort rule. Fixed by replacing `redact.paths` with a `formatters.log` hook (`deepRedact`) that recursively walks the entire object pino is about to serialize, at any depth, under any parent key or inside an array, before any config-driven path matching would even apply. **Second amendment, written here after a fresh re-review (retry 2) of that same fix**: `formatters.log` alone still left the real `Authorization: Bearer <token>` header logging in plaintext on every authenticated request, live-reproduced — because `pino-http` attaches `req`/`res` to each request's child logger as *bindings* (`logger.child({req, res})`), which pino serializes via its own `serializers.req`/`serializers.res` functions, a pipeline stage `formatters.log` never sees (it only sees the object passed directly to a given `log()` call). Fixed by also adding `pinoHttp.serializers.req`/`.res` in `app.module.ts`, each wrapping pino's own default serializer (`pino.stdSerializers.req`/`.res`) and running `deepRedact` over its output before returning — live-verified afterwards: a real authenticated `GET /me` request now logs `"authorization":"[REDACTED]"` with zero occurrences of the raw token or password anywhere in the log output, while `requestId`/`userId`/`route`/`durationMs` remain correct with no duplicate-key regression. **Third amendment, written here after a second fresh re-review (retry 3) of the same fix**: a real `GET /files/:id?token=...` request (WU-06's own endpoint) still leaked the file-access token in plaintext, live-reproduced — not a regression of either prior fix, but a different mechanism entirely: `deepRedact` only matches sensitive object *keys*, so while it correctly redacted `query.token`, it had no way to notice the identical token value also present, unredacted, as a substring inside the adjacent `url` string field (pino's default `req` serializer includes the raw path+query verbatim). ## User Story 1: Provision a company and its first administrator (added after WU-01–WU-05)

This section covers `tasks.md`'s Phase 3 (T042–T045) — not part of the original Setup+Foundational scope this plan was written for, but following the exact same WU structure/review discipline, added once WU-01–WU-05 made it buildable (WU-05 gave System Admin a real, working login; this is the first thing they can do with it).

### A real design gap found before implementation: `POST /companies` under RLS

`POST /companies` must be an **authenticated** route (System Admin only — `@Roles('SYSTEM_ADMIN')`), not `@Public()`. That matters because of exactly how `TransactionInterceptor` (WU-03/WU-04) currently works: for any non-`@Public()` route, it opens a transaction and sets `app.company_id` from `cls.get('companyId') ?? ''` — but **nothing currently populates that CLS value**. Architecture §4's `TenantContextInterceptor` (the piece that would read a tenant user's `companyId` off their verified JWT into CLS) is explicitly deferred to a later slice (noted in both WU-03 and WU-04's own design notes) — correct for now, since no ordinary tenant-scoped route exists yet to need it. The consequence: `cls.get('companyId')` is *always* `''` today, so `TransactionInterceptor` always sets `app.company_id = NULL` (via the NULLIF guard) for every authenticated route — which means a naive `POST /companies` handler using the interceptor's own `tx` would have its `User` insert (the first Company Admin) silently rejected by RLS, since neither `app.company_id` matches a real company nor `app.is_system_context` is set.

**Decision**: add a `@SkipTenant()` decorator (the exact mechanism Architecture §5 already names for System Admin routes, not a new invention) that `TransactionInterceptor` checks alongside `@Public()` — but unlike `@Public()` (which skips the transaction entirely), `@SkipTenant()` still opens one, just sets `app.is_system_context = 'true'` instead of `app.company_id`. This is the only kind of transaction a `SYSTEM_ADMIN`-only route ever needs (they have no company to scope to), so this mapping is unconditional for this decorator — no runtime branching on which session variable to set. `RolesGuard`'s existing `@Roles('SYSTEM_ADMIN')` check (WU-04) is what actually enforces that only a System Admin reaches the handler at all; `@SkipTenant()` only changes which RLS context the resulting transaction runs under.

**DoD** (per `contracts/companies.md`, `tasks.md` T042–T045):
1. A `@SkipTenant()` decorator (metadata-only, same shape as `@Public()`) that `TransactionInterceptor` reads via `Reflector` and, when present, sets `app.is_system_context = 'true'` instead of reading `cls.get('companyId')` — added to `transaction.interceptor.ts` itself, the same file WU-04 already amended once for `@Public()`.
2. A role-seeding helper (`apps/api/src/modules/roles/roles.seed.ts`): given a `companyId`, inserts the company's four tenant-scoped roles (`COMPANY_ADMIN`, `MANAGER`, `MARKETING_EXECUTIVE`, `EMPLOYEE`) with `permissions` mirrored from PRD §3's matrix. (The platform-wide `SYSTEM_ADMIN` role already exists, seeded once by WU-05's `seed.ts` — this helper does not touch it.)
3. `POST /companies` (`@Roles('SYSTEM_ADMIN')`, `@SkipTenant()`, `Idempotency-Key` required): in one transaction, creates `Company` (rejecting a duplicate `code` as `409 COMPANY_CODE_TAKEN`), its `CompanySettings` row with architecture defaults, the four seeded roles (via the helper above), and the first `User` with `role.key = COMPANY_ADMIN` built from the request's nested `admin` object (name, email, username, temporaryPassword, mobile) — password hashed via WU-05's `password.ts`. Writes one `AuditEvent`.
4. `GET /companies` (`@Roles('SYSTEM_ADMIN')`, `@SkipTenant()`): cursor-paginated, returns `{ id, code, name, status, timezone, createdAt }[]`.
5. `PATCH /companies/:id` (`@Roles('SYSTEM_ADMIN')`, `@SkipTenant()`): optional `{ name, place, contactEmail, contactPhone, status }`; setting `status: SUSPENDED` takes effect at each affected user's next sign-in (enforced already by `ActiveAccountGuard`, WU-04 — no new code needed for that part, just confirm it in testing).
6. `CompaniesModule` registered in `app.module.ts`'s `imports` — verified concretely: boot the app, confirm the three routes are mapped, then the Human Checkpoint below (a real `POST /companies` call, followed by a real login as the admin it just created) as end-to-end proof.

**File scope**: `apps/api/src/common/decorators/skip-tenant.decorator.ts` (new), `apps/api/src/common/interceptors/transaction.interceptor.ts` (adding the `@SkipTenant()` check only — same pattern as WU-04's `@Public()` addition), `apps/api/src/modules/roles/roles.seed.ts` (new), `apps/api/src/modules/companies/{companies.controller,companies.service,companies.module}.ts` (new), `packages/shared/src/companies.schema.ts` (new, request/response Zod shapes) + `packages/shared/src/index.ts` (exports only), `apps/api/src/app.module.ts` (register `CompaniesModule` only). **Amendment, written here after this story's own checkpoint review**: also `apps/api/src/common/guards/require-idempotency-key.guard.ts` (new) — live verification found `POST /companies` accepted a request with NO `Idempotency-Key` header at all (`201`, a real company created with zero duplicate-submission protection), because WU-04's `IdempotencyInterceptor` deliberately treats the header as optional-when-absent by design, leaving "this route's contract requires it" enforcement to the route itself — a job nothing had done yet. ## User Story 3: Company Admin manages users, starting with creating one (added after User Story 2)

Covers `tasks.md`'s Phase 5 (T053–T061). The first module where `TransactionInterceptor`'s *ordinary* (non-`@SkipTenant()`, non-`@Public()`) branch actually matters for more than a single-row self-lookup, and the first endpoint that accepts a photo upload with no pre-existing owner.

### Seven real gaps found during planning/plan review

**1. `contracts/users.md`/`contracts/files.md` disagree on how a new user's photo gets uploaded, and neither describes a working mechanism on its own.** `contracts/users.md`'s `POST /users` request lists `photoFileId?: string` — implying the client already has a file id before calling it. `contracts/files.md` says the opposite: "there is no standalone `POST /files`... a bare upload-then-attach two-step isn't needed yet because every avatar upload already has a known owner at upload time" — but that reasoning was written for the self-service case (`PATCH /me/photo`, User Story 4, not yet built); it doesn't hold here, since **the new user doesn't exist yet** at the moment their photo is chosen on the User form (T059/T060). Neither contract actually specifies a mechanism that produces a `photoFileId` before the user is created.

**Decision**: add one new, narrowly-scoped endpoint, `POST /files/avatars` (`@Roles('COMPANY_ADMIN')`, ordinary authenticated — not `@Public()`, not `@SkipTenant()`): multipart, single file, calls `FilesService.uploadAvatar()` (already built, WU-06, unchanged) with the *acting admin's own* `companyId`/`id` as the owner metadata, returns `{ id, url }`. The mobile User form (T060) uploads through this route first, then submits `POST /users`/`PATCH /users/:id` as plain JSON with the returned id as `photoFileId` — exactly matching `contracts/users.md`'s literal schema, and exactly matching T060's own wording ("upload through multipart... before submit, attaching the returned file id"). No standalone `POST /files` for *reading*/listing is added — only this one upload route, and only because US3 is the first story where an avatar's owner genuinely doesn't exist yet at upload time, which is a real, narrow exception to `contracts/files.md`'s stated rule, not a reversal of it. `contracts/files.md` is updated to document this endpoint and correct its "not needed yet" claim to note this one exception.

This also sidesteps a genuine pipeline-ordering hazard: `IdempotencyInterceptor` (global, WU-04) hashes `request.body` *before* any controller-level interceptor (like multer's `FileInterceptor`) has parsed a multipart body — had `POST /users` itself been made multipart-capable (the alternative design), its own `Idempotency-Key` requirement (contracts/users.md) would have hashed an empty/unparsed body on every request, silently defeating the "same key, different body → 409" protection for that route. Keeping `POST /users`/`PATCH /users/:id` pure JSON (as both contracts' literal schemas already specify) avoids this entirely. `POST /files/avatars` itself **does** require `Idempotency-Key` too (found by plan review): CLAUDE.md Constitution rule 3 — "every state-changing POST takes an `Idempotency-Key`" — is stated with no exception for a route that happens to have its own, separate content-based dedupe; `FilesService.uploadAvatar()`'s `sha256` dedupe and a stored `Idempotency-Key` replay solve two different problems (identical bytes retried under a different/no key, vs. an exact retry under the same key) and are not substitutes for each other.

Applying `RequireIdempotencyKeyGuard` here is safe despite the same multipart-body-hashing hazard gap #1 identifies for why `POST /users` itself must stay pure JSON — but for a structurally different reason, worth spelling out precisely: `IdempotencyInterceptor.hashRequest()` reads `request.body`, which Express's body parsers never populate for a `multipart/form-data` request (multer hasn't run yet at that point in the pipeline, and nothing else will parse it) — so `request.body` is `undefined`/`null` on *every* call to this route, regardless of the actual file bytes, deterministically. That means two calls presenting the *same* `Idempotency-Key` always hash identically (both hash `{method, url, body: null}`), so a genuine retry (same key, same file, e.g. a timeout) correctly replays the stored response — the behavior this route actually needs. The one case this degrades is a key reused across two *different* uploads, which would also replay the first response rather than 409 — not a security issue (no unauthorized data is returned), just a lost "reused key" detection for this one route; `uploadAvatar()`'s own `sha256` dedupe already makes that scenario low-stakes in practice (Constitution rule 3's own premise — a fresh ULID key is minted per logical action — means a genuinely different upload should arrive under its own, different key to begin with).

**2. `FilesController`'s class-level `@Public()` would leak onto the new route.** `@Public()`/`@Roles()`/every other guard's metadata check uses `Reflector.getAllAndOverride(KEY, [handler, class])` — the first non-`undefined` value wins, checking the handler before the class, but there is no way to *unset* a class-level `true` at the method level (there is no `@Public(false)`). Today `@Public()` sits on the whole `FilesController` class (correct while it had exactly one route, `GET /files/:id`, which genuinely has no JWT). Adding `uploadAvatar` as a second method on that same class would silently make it public too.

**Decision**: move `@Public()` from the class down to the `getFile` method specifically — the more correct granularity now that the class has a route that must NOT be public. **Not pure relocation on its own** (found by plan review): `@Roles(...)` metadata has no effect unless `RolesGuard` is actually applied — this codebase's `roles.decorator.ts` says so explicitly, and every existing `@Roles()` usage (`CompaniesController`) pairs it with `@UseGuards(RolesGuard)`; `FilesController` today has no guards applied at all. So this change also adds `@UseGuards(RolesGuard)` to `FilesController` (class level — harmless for the existing `getFile` method, since `RolesGuard` returns `true` unconditionally for any handler/class with no `@Roles()` metadata, confirmed in `roles.guard.ts`'s own logic) alongside the `@Roles('COMPANY_ADMIN')` on the new method. Without this, `POST /files/avatars` would be reachable by any authenticated active user regardless of role, not just a Company Admin.

**4. (Found by plan review) Username uniqueness is case-insensitive by rule (FR-006: "unique within a company, case-insensitive") but the only DB constraint that exists (`@@unique([companyId, username])`, WU-02) is a plain, case-*sensitive* Postgres unique index.** This is a pre-existing gap from WU-02/US1 — `companies.service.ts`'s own admin-creation path has no duplicate-username check at all (relies solely on this constraint) — but it has never been exercised: a brand-new company's first admin can't collide with anything yet. This story is the *first* place duplicate-username rejection is a live, required feature (DoD item 3's `409 USERNAME_TAKEN`, FR-006/FR-018), and spec.md's own Edge Cases section requires this to hold even under a race ("two administrators try to create a user with the same username in the same company at the same moment — exactly one save succeeds") — an application-level pre-check (`findFirst` with `mode: 'insensitive'` before `create`) is TOCTOU-vulnerable on its own and cannot guarantee that.

**Decision, revised after plan review itself flagged the first version of this fix as scope creep**: `tasks.md`'s own T011 (WU-02, already built and committed before this story) deliberately paired FR-006's case-insensitive business rule with a plain, case-*sensitive* `@@unique([companyId, username])` Prisma attribute, leaving case-insensitive enforcement to the application layer — T054's own literal wording, `"(companyId, lower(username))"`, is fully satisfiable by an app-level check, with no DB change implied. Altering that already-reviewed WU-02 schema/migration is a bigger, separate decision than "start user story 3 T053-T061" asked for, so this plan does **not** do that. Instead: `UsersService.create()` runs a `findFirst({ where: { companyId, username: { equals: input.username, mode: 'insensitive' } } })` check inside the same transaction as the subsequent `user.create()` call (narrowing, though not eliminating, the race window — a second transaction racing to commit between the check and the insert, under Postgres's default READ COMMITTED isolation, could still both pass the check) immediately before the insert, matching the exact pattern `auth.service.ts`'s login lookup already uses (`mode: 'insensitive'`) for consistency. **This leaves spec.md's Edge Cases concurrency scenario ("two administrators... at the same moment... exactly one save succeeds") as a known, pre-existing, narrow residual risk — not fixed by this story, not newly introduced by it either (the exact same gap already exists, unexercised, in `companies.service.ts`'s admin-creation path since WU-02/US1) — and explicitly surfaced here rather than silently inherited, as a candidate for a future, explicitly-requested fix (a case-insensitive DB index) if the business ever needs that guarantee to be airtight rather than merely highly-likely.**

**3. The mobile API client (`apps/mobile/src/api/client.ts`, US2) has no multipart support.** `rawFetch()` unconditionally sets `Content-Type: application/json` and `JSON.stringify()`s the body — both wrong for a `FormData` upload (which needs `fetch` to set its own multipart boundary header, and the raw `FormData` object as the body, not a JSON string). **Decision**: extend `rawFetch`/`apiRequest` with a branch — when `options.body instanceof FormData`, skip the `Content-Type` header and pass the `FormData` through unmodified — rather than writing a parallel one-off multipart function, so the upload call still gets the existing 401-refresh-retry logic for free.

**5. (Found by plan review) `monthlySalary` versioning and role-change versioning — two more apparent FR-020/Edge-Cases conflicts, resolved differently.**

spec.md's Edge Cases section has a bullet reading *"What happens if someone edits a user's monthly salary or half-day rate? The change is recorded as a new, dated entry..."* — grouping `monthlySalary` with `halfDayRate`. But the actual numbered, authoritative requirement, **FR-020**, is narrower: *"System MUST record every change to a user's **role or half-day rate** as a new, dated entry"* — `monthlySalary` is not in FR-020 at all, and `data-model.md`'s `User` entity (already written, already reviewed, well before this story) gives `halfDayRate` its own versioned `UserSalaryRate` table but leaves `monthlySalary` a single plain scalar column, with no versioning structure. Given FR-020 is the specific, numbered requirement and the Edge Cases bullet is looser illustrative prose that doesn't even agree with FR-020 (compare "role or half-day rate" vs "monthly salary or half-day rate" — these are two different pairs), and given `data-model.md`'s already-settled schema already reflects FR-020's narrower scope rather than the Edge Cases bullet's: **this plan treats the Edge Cases bullet's inclusion of `monthlySalary` as a pre-existing drafting inconsistency in `spec.md` itself, not a requirement this story must satisfy** — `PATCH /users/:id`'s plain overwrite of `monthlySalary` (DoD item 4) matches FR-020's actual scope and `data-model.md`'s actual schema. Retrofitting salary history for `monthlySalary` with no dedicated versioning table is a `data-model.md`-level decision, out of scope for "start user story 3."

FR-020's other half — role changes needing a "new, dated entry" — genuinely has no implementation anywhere in this slice, but that is `contracts/users.md`'s own, already-written, already-reviewed decision (predating this plan): *"Role is **not** patchable here in this slice ... no story requires it yet."* Neither `tasks.md`'s literal T053–T061 nor any DoD item in this story's own list ever mentions changing a role. This plan does not reopen that decision (doing so — adding role-change history tracking with no task asking for it — would be exactly the kind of scope creep gap #4's first draft was correctly called out for) — but it does fix the one concrete, in-scope UI consequence the backend restriction creates: `UserFormScreen.tsx`'s role picker (DoD item 10) must render **disabled/read-only in edit mode** (selectable only when creating a new user), so the form never implies a role change is possible when the backend silently cannot accept one.

**6. (Found by plan review) `contracts/auth.md` requires `Idempotency-Key` on every mutating endpoint "under Companies/Users," not just `POST /users`.** Its exact text: *"All five mutating endpoints above (`reset-password`, `change-password`, and anything under Companies/Users below) require an `Idempotency-Key` header."* `contracts/users.md` itself only repeats this explicitly for `POST /users`, staying silent for `PATCH /users/:id` and `POST /users/:id/salary-rates` — but `contracts/auth.md`'s blanket statement already covers both, and Architecture D-15 ("`Idempotency-Key` on every command") independently doesn't limit itself to the POST HTTP verb either (**correction, found during User Story 4's planning**: this line originally cited "Constitution rule 3" for the verb-agnostic point, but both `CLAUDE.md`'s rule 3 and Architecture §21's own numbered rule 3 are explicitly POST-scoped — "every state-changing POST"/"every POST that changes state" — D-15 is the only genuinely verb-agnostic source in this project's own documents, and is the correct citation here). Without this, a double-tapped `PATCH /users/:id { halfDayRate, rateEffectiveFrom }` or `POST /users/:id/salary-rates` retry could insert two closed-plus-new-open-ended `UserSalaryRate` pairs instead of one — directly undermining the append-only guarantee DoD item 5 exists to provide (Constitution rule 4). **Decision**: apply `RequireIdempotencyKeyGuard` (reused as-is, same guard `POST /users`/`POST /companies` already use) to both `PATCH /users/:id` and `POST /users/:id/salary-rates` too. (Note, surfaced but out of this story's scope to retrofit: `PATCH /companies/:id`, User Story 1, has this exact same gap under the same contract sentence — not fixed here, since that endpoint is already committed and not part of T053-T061.)

**7. (Found by plan review) `UserSalaryRate` is a genuine tenant table — its own, always-non-null `companyId` column (`schema.prisma`) — but is missing from *both* isolation layers Constitution rule 2 requires ("a new tenant table missing either layer must fail CI").** `tenant.extension.ts`'s `TENANT_MODELS` set (WU-03/T019) contains only `User`/`FileObject`; the RLS migration (WU-03/T020) enables `ENABLE`/`FORCE ROW LEVEL SECURITY` only for `users`/`file_objects`. Neither oversight was deliberate the way gap #4's username-constraint split was — `UserSalaryRate` simply never had a real write path before this story (`POST /users`, DoD item 3, is the first code anywhere that will insert into it), so WU-03 had nothing yet to apply its own rule to. This story is the first to need it, so this story closes it, the same way WU-03's own adversarial review once found and fixed `FileObject` needing the identical `is_system_context` escape `User` already had.

**Decision**: (a) add `UserSalaryRate` to `TENANT_MODELS` in `tenant.extension.ts`; (b) a new migration enabling RLS for `user_salary_rates`, mirroring `users`/`file_objects`'s existing policy **exactly**, including the detail a first draft of this gap got wrong (found by plan review): `UserSalaryRate.companyId` is `String` (plain TEXT, like `users.company_id`/`file_objects.company_id` — Prisma generates the uuid value client-side as a string, there is no native Postgres `uuid` column anywhere in this schema), so the policy must use the same fail-closed `NULLIF(current_setting('app.company_id', true), '')` guard those two already use — **not** a `::uuid` cast, which the existing migration's own comment explicitly documents as inapplicable to this schema and which would raise a Postgres error (not fail closed) on an unset/empty session variable. Simpler than `users`/`file_objects` in only one respect — no `is_system_context` OR-branch, since `UserSalaryRate.companyId` is never `NULL` (no `SYSTEM_ADMIN`-style exception exists for salary rows): `USING ("company_id" = NULLIF(current_setting('app.company_id', true), '')) WITH CHECK ("company_id" = NULLIF(current_setting('app.company_id', true), ''))`. Unlike gap #4's reverted migration attempt, this is not reopening an already-reviewed, deliberate WU-02 decision to satisfy a want this story introduces — it is completing WU-03's own already-stated, not-yet-fully-applied rule for a table no story had written to until now. Every `tx.userSalaryRate.*` call in `UsersService` (DoD items 3, 5, 6) then gets both layers for free, the same way `tx.user.*` does per the "On tenant scoping" section below.

## User Story 4: View and update own profile, recover a forgotten password (added after User Story 3)

Covers `tasks.md`'s Phase 6 (T062–T070). The first story with no new migration at all — `OtpChallenge` already has every field this story needs (WU-02) — but the most security-sensitive one yet: it's the only place in this codebase that authenticates a request with no password at all (a 6-digit code) and the only place that must actively resist username enumeration by design.

### Design decisions made before implementation

**1. `resetToken` is a stateless, HMAC-signed reference to an `OtpChallenge` row — not a JWT, and not a new DB column.** `contracts/auth.md` calls it "a short-lived (10 min), single-purpose token for the next call only," and `POST /auth/reset-password`'s own heading says "requires `resetToken` (bearer)" even though its literal request body already carries `resetToken` as a field — read together, that heading means "this route's authority comes from presenting a valid resetToken," not literally `Authorization: Bearer <resetToken>`; the route stays `@Public()`, verifying `resetToken` itself inside the handler.

Two real alternatives considered and rejected: (a) sign it with the same `jwtService`/`JWT_ACCESS_SECRET` `TokenService` already uses for access tokens — rejected, since `JwtAuthGuard.canActivate()` calls `jwtService.verify<AccessTokenPayload>(token)` with no runtime check that the decoded payload actually *has* those fields (a TypeScript generic is compile-time only) — a resetToken signed with the same secret could be misinterpreted as a (garbage but signature-valid) access token by a route that forgot to check its shape, a real cross-boundary risk; (b) add a new `OtpChallenge` column to store a resetToken's own hash — rejected as an unnecessary schema change (this story's own stated no-migration goal) once decision #2's design confirms `consumedAt` already covers what a dedicated column would have been for.

**Decision**: mirrors `files.service.ts`'s existing `signToken`/`verifyToken`/`hmac`/`safeEqual` pattern exactly (WU-06), with its own dedicated secret rather than reusing `FILE_URL_SECRET` (a genuinely separate security boundary — file-serving authority and password-reset authority should not share a key). Payload: `${otpChallengeId}|${userId}|${exp}`, HMAC-SHA256'd with a new `PASSWORD_RESET_SECRET` env var (added to `packages/shared/src/env.ts`'s schema the same way `FILE_URL_SECRET` already is, plus `.env`/`.env.example`). Verification looks up the `OtpChallenge` by id, confirms `userId` matches, and confirms it's still genuinely live (decision #2, below).

**2. `OtpChallenge.consumedAt` is set at `verify-otp` time, exactly as `tasks.md` T064 literally specifies — a first draft of this plan got this wrong (found by plan review) by over-engineering a one-time-use guarantee for `resetToken` itself that neither T064, `data-model.md`'s own field table ("`consumedAt` ... Set once a correct code is accepted"), nor any spec.md acceptance scenario actually asks for.** The first draft deferred `consumedAt` to `reset-password` instead, reasoning from `data-model.md`'s looser "state transitions" prose line while skipping over that same document's own, more specific field-table description two lines above it — and while directly contradicting T064's unambiguous text ("on a correct code within the window, marks `consumedAt` and returns a short-lived `resetToken`"). That was solving a problem (can a `resetToken` be replayed against `reset-password` more than once inside its own 10-minute window?) this story was never asked to solve, at the cost of silently diverging from what T064 literally says `verify-otp` must do.

**Decision**: `verify-otp` sets `consumedAt` on a correct code, exactly as written. `reset-password`'s own `resetToken` check becomes simpler, not more complex, as a result: decode + HMAC-verify the token, look up the `OtpChallenge` by id, confirm `userId` matches, confirm `consumedAt IS NOT NULL` (proving a correct code really was accepted for this challenge — the inverse of every other check in this codebase that gates on a timestamp being *null*, since here the token's whole premise is "this already happened") and that the token's own embedded `exp` hasn't passed. This does mean a still-unexpired `resetToken` could in principle be presented to `reset-password` more than once inside its 10-minute window — not prohibited by any literal requirement in scope here (`contracts/auth.md`'s error vocabulary for this route is only `VALIDATION_FAILED`/`TOKEN_EXPIRED`, with no "already used" code to report), and not a security hole beyond what the 10-minute expiry already bounds. If stricter single-use ever becomes an explicit requirement, that is a separate, explicitly-requested follow-up, not something to invent unilaterally here.

**3a. (Found by plan review — a real gap in `contracts/auth.md` itself, predating this plan) `forgot-password`/`verify-otp`'s request shape is `{ username }` alone, with no `companyCode` — but `User.username` is only unique *per company* (`@@unique([companyId, username])`, FR-006: "may repeat across different companies").** A bare-username lookup with no company to scope it to is genuinely ambiguous the moment two different companies happen to have the same username, and `AuthService.findCandidate()` (the exact lookup this story's own decision #3b/DoD item 3 says it mirrors) requires a `companyId` to run its RLS-scoped query at all — there is no existing "scan every company" fallback anywhere in this codebase, nor should there be one (that would mean a forgotten-password request for one company's `"admin"` could silently target a *different* company's `"admin"` row, a direct Constitution rule 2 tenant-isolation violation, not merely a usability bug). `contracts/auth.md`'s own `POST /auth/login` already solves the identical problem with an optional `companyCode` field (omitted only for `SYSTEM_ADMIN`) baked into the mobile build config (`apps/mobile/src/config.ts`'s `COMPANY_CODE`, already used by `SignInScreen.tsx`) — `forgot-password`/`verify-otp` simply never got the same field added when `contracts/auth.md` was originally written.

**Decision**: `forgotPasswordSchema`/`verifyOtpSchema` both add the identical optional `companyCode` field `loginSchema` already has (same bounds, same "omitted only for `SYSTEM_ADMIN`" semantics). `ForgotPasswordScreen.tsx` (DoD item 10) sends `COMPANY_CODE` the same way `SignInScreen.tsx` already does for login — no new mobile-side concept, just the same build-time constant reused on a second screen. `contracts/auth.md` is updated to add `companyCode?: string` to both request shapes, documenting this as a correction rather than silently diverging from the written contract.

**The `companyId` *resolution* deliberately does NOT mirror `login()`'s error behavior (found by plan review)**: `login()` throws a distinguishable `INVALID_CREDENTIALS` the moment `companyCode` fails to resolve to a real `Company` — correct there, since `login()` has no enumeration-resistance requirement to begin with (a wrong company code and a wrong username already produce the identical error/message, by design). `forgot-password`/`verify-otp` do have that requirement (decision #3b, `contracts/auth.md`'s own "same shape and timing" clause) — so copying `login()`'s *error-throwing* behavior here would itself become a brand-new side channel: a bad `companyCode` would throw while a bad `username` returns `200`, letting an attacker learn whether a company code exists at all. **Decision**: only the *lookup mechanism* mirrors `login()` (same `Company.findUnique({ where: { code } })` call); the *outcome* on failure does not — an unresolvable `companyCode` joins the exact same "doesn't exist" bucket as an unresolvable `username` (decision #3b), collapsing to the identical generic `200 { maskedMobile }` with no distinguishable error, before `User`/`OtpChallenge` is ever touched.

**3b. `forgot-password`/`verify-otp` must not let an attacker distinguish "username doesn't exist," "username exists but has no mobile on file," and "username exists, has a mobile, but I got the OTP code wrong" from each other — every one of these collapses to the same response shape.** `contracts/auth.md` already states the "same shape and timing" requirement for `forgot-password` itself, but doesn't explicitly address two cases found while designing this: a user with no `mobile` on file (possible today — `createCompanyAdminSchema`, User Story 1, has always made `mobile` optional, predating User Story 3's later, stricter rule for `POST /users`, so an existing admin created via `POST /companies` may genuinely have none), and `verify-otp` being called for a username that never requested one at all (no live `OtpChallenge` row to check against).

**Decision**: `forgot-password` treats "doesn't exist," "exists but `mobile` is null," and "exists, has a mobile, but is within the 30-second resend cooldown of its own last challenge" identically — always `200 { maskedMobile }`, with a fixed, generic placeholder mask for the first two cases (indistinguishable from a real one by shape) and silently not creating a new challenge/not calling `SmsAdapter.send()` for any of the three. `verify-otp`, given no live (`consumedAt: null`, `expiresAt` in the future) `OtpChallenge` exists for a username at all (because it never existed, never requested one, or already fully consumed one), reports the same `OTP_INCORRECT` the contract already defines for a genuinely wrong code — never a distinct "no such challenge" signal.

**On "identical timing" (found by plan review)**: the contract's "same shape and timing" phrase is only partially achievable without disproportionate engineering, and this codebase already has a precedent for exactly that tradeoff — `auth.service.ts`'s own `login()` short-circuits `passwordOk` to `false` without ever calling `password.verify()` when no `candidate` was found (`candidate?.passwordHash && (await password.verify(...))`), making a nonexistent-username login measurably faster than a real one, and that asymmetry was never flagged as a gap through WU-05's own review. `forgot-password` matches that same standard rather than inventing new constant-time machinery nothing else here uses: it always performs the one DB lookup (case-insensitive `findFirst`, same cost whether or not a row comes back), and only the genuinely-different-cost tail — minting+hashing a real OTP and calling `SmsAdapter.send()` — differs between branches. In production, that tail is dominated by a real SMS gateway's own network latency (highly variable regardless of anything this code does), not server CPU time, which is the actual reason this contract clause is satisfiable in spirit without a dedicated dummy-work mechanism; a true constant-time guarantee is not implemented and not claimed.

**On the masked-mobile format (found by plan review)**: neither `contracts/auth.md` nor `data-model.md` defines a masking algorithm, and the two illustrative examples already in this repo disagree in shape (`contracts/auth.md`: `"+91•••••••123"`, 3 digits visible; `quickstart.md`: `"+91•••••••22222"`, 5 digits visible, an internally inconsistent total length for a plausible phone number). **Decision**: the contract file's own example is authoritative (quickstart.md is a looser walkthrough illustration, not a contract). Algorithm: keep the first 3 characters of `mobile` as-is, mask every character from index 3 up to (length − 3) with `•`, keep the last 3 characters as-is — applied to a 13-character E.164 Indian number (`+91` + 10 digits) this reproduces the contract's own example exactly (3 kept + 7 masked + 3 kept = 13). The fixed placeholder used for the "doesn't exist"/"no mobile" branches above is this same algorithm applied to one fixed dummy number, so it's shape-identical to a real mask by construction, not a separately-invented format.

**Found by plan review, same decision**: `mobile` itself has no format constraint anywhere in this codebase — `createCompanyAdminSchema` (User Story 1) and `createUserSchema` (User Story 3) both declare it `z.string().min(1).max(32).optional()`, no regex, so a value far shorter than a real E.164 number is already schema-legal today (e.g. a placeholder a System Admin typed on `POST /companies`). Applying "first 3 / mask middle / last 3" to a short string either overlaps or exceeds its length, producing a garbled, wrong-shape mask instead of a safe one. **Decision**: the masking function falls back to the same fixed generic placeholder already used for the "doesn't exist"/"no mobile" cases whenever `mobile.length < 8` (comfortably below any plausible real mobile number's length, including without a `+CC` prefix), rather than slicing a string too short to mask meaningfully — treating "a mobile on file too short to mask" the same, deliberately, as "no mobile on file at all."

**4. `research.md #5`'s `LogSmsAdapter` (debug-level OTP logging for local dev, no real SMS gateway yet) would be silently defeated by WU-07's `deepRedact` if the OTP is logged as a structured field.** `deep-redact.ts`'s `SENSITIVE_KEYS` set already includes `'otp'` literally, and `main.ts`'s `app.useLogger(app.get(Logger))` (the `Logger` itself configured by `app.module.ts`'s `LoggerModule.forRoot(...)`, Architecture §18/WU-07) makes *every* Nest `Logger` instance in this process — not just pino-http's own HTTP request/response logging — pino-backed and therefore run through `formatters.log`'s `deepRedact`. A naive `this.logger.debug({ event: 'sms.send', to, otp: code })` would log `otp: "[REDACTED]"`, making the whole point of this adapter (seeing the code locally without a real SMS bill) impossible. `deepRedact` only ever matches by object *key* (a limitation WU-07's own review found and documented three times over) — it has no way to catch a value embedded as a substring inside an unrelated string.

**Decision**: `LogSmsAdapter.send()` logs the already-composed SMS `message` string itself (e.g. `this.logger.debug(\`[LogSmsAdapter] -> ${toE164}: ${message}\`)`), never a structured `{ otp: code }` field — the OTP reaches the log exactly the way research.md #5 intends (visible for local testing), by construction rather than by exploiting `deepRedact`'s known blind spot. This is the one place in this codebase an OTP is deliberately allowed to appear in a log line, and it's load-bearing that it stays that way *only* at `debug` level (never emitted under this project's default `LOG_LEVEL=info`) and *only* in this one adapter, never through the request-logging pipeline those other three redaction rounds were fixing.

**4b. (Found by plan review) `deep-redact.ts`'s `SENSITIVE_KEYS` set doesn't contain any of this story's own new field names.** `resetToken`, `currentPassword`, `newPassword`, `confirmPassword` are all genuinely new, unambiguous, sensitive-only key names a future handler could log by accident (the same "even if a future handler logs a body/header containing one" scenario `app.module.ts`'s own `LoggerModule` comment names as the reason this list exists at all). **Decision**: add all four. Deliberately **not** adding bare `code` (verify-otp's own 6-digit-OTP request field) — `code` is also this codebase's existing, non-sensitive field name for a `Company.code` and for every `ProblemDetails.code` (the error-code string every failed response already carries), and `deepRedact` matches by exact key with no path-scoping, so adding it would redact those too, actively hurting observability for no live benefit: pino-http's own `req` serializer never includes `req.body` at all (confirmed repeatedly during WU-07's own adversarial review rounds), so nothing in this codebase's actual logging path would ever expose a request body's `code` field in the first place — this is a defense-in-depth gap being knowingly left open, not a live leak, and renaming the wire field itself would be an unrequested contract change.

**5. `FilesService.uploadAvatar()`'s `companyId` parameter is `string`, not `string | null` — but `PATCH /me/photo` (`contracts/me.md`) is "any authenticated role," which includes `SYSTEM_ADMIN` (`companyId: null`).** `contracts/me.md`'s `GET /me` already returns `company: null` for exactly this case, so this story can't quietly assume every caller has a real company the way `POST /files/avatars` (User Story 3, `@Roles('COMPANY_ADMIN')` only) safely could.

**Decision**: widen `uploadAvatar`'s `companyId` parameter to `string | null`, mirroring the `string | null` shape `getForServing`/`signFileUrl` already use in the same file — inside its own transaction, set `app.is_system_context` instead of `app.company_id` when `companyId` is `null` (the exact escape `auth.service.ts`/`active-account.guard.ts` already use for the identical reason), and dedupe `FileObject` rows the same way `User` rows already group under a `null` companyId (a plain `where: { companyId: null, ... }` Prisma filter already means "rows where this column is literally null," no special-casing needed beyond the RLS session variable). `MeService.updatePhoto()` then calls it with `payload.companyId` as-is, no caller-side branching.

**Also found by plan review, same decision**: `uploadAvatar`'s `storageKey`/`thumbKey` construction (`` `photos/${companyId}/${yyyy}/${mm}/${id}.webp` ``) template-interpolates `companyId` directly — for `companyId: null`, JavaScript's template-literal coercion would silently write the literal path segment `"photos/null/..."`, not a crash but a real, wrong, confusing-to-debug storage path. Fixed by reusing this same file's own existing `NULL_COMPANY_SENTINEL` constant (`'-'`, already defined and already used for exactly this null-companyId case in the signed-token payload) for the path segment too, instead of letting `companyId` flow into the template literal unguarded.

**Also found by plan review**: `MeService.updatePhoto()` calling `FilesService.uploadAvatar()` needs `FilesService` injected via Nest's DI container, which only resolves across modules through an explicit `imports` entry — `FilesModule` is not `@Global()`. `me.module.ts` today has no `imports` array at all. `UsersModule` (User Story 3) already solved the identical need — `UsersService` itself does constructor-inject `FilesService` (for `signFileUrl()`, building each listed user's `photoUrl`), which only works because `users.module.ts` already declares `imports: [FilesModule]` — `me.module.ts` needs the exact same one-line addition for the identical reason, or this story fails at Nest bootstrap with a dependency-resolution error, not at runtime.

**6. `PATCH /me/photo` DOES require `Idempotency-Key` — a first draft of this plan exempted it, inconsistently with how User Story 3's gap #6 treated the structurally identical question for `PATCH /users/:id` (found by plan review, corrected again on a second pass after the first correction's own citation turned out to be wrong — see below).** `contracts/auth.md`'s blanket Idempotency-Key sentence only names `reset-password`/`change-password` plus "anything under Companies/Users below" — `contracts/me.md` is a separate file that sentence never mentions, and `contracts/me.md` itself said nothing about Idempotency-Key for this route either. The first draft stopped there and treated that textual silence as dispositive.

User Story 3's gap #6 did not stop at `contracts/users.md`'s identical silence for `PATCH /users/:id` — it additionally reasoned that the requirement "doesn't limit itself to the POST HTTP verb," attributing that to "Constitution rule 3." That attribution was itself wrong, caught only on a second pass here: `CLAUDE.md`'s rule 3 and Architecture §21's own numbered rule 3 are both explicitly scoped to POST ("every state-changing POST"/"every POST that changes state"), not verb-agnostic at all. The one genuinely verb-agnostic source in this project's documents is Architecture **D-15** ("`Idempotency-Key` on every command") — gap #6's conclusion (apply the guard to `PATCH /users/:id` too) was right, but its stated reason was citing the wrong rule, now corrected in gap #6's own text above.

**Decision**: with the citation now correct, the underlying inconsistency this item exists to fix still holds — exempting `PATCH /me/photo` using only "no contract file mentions it" while `PATCH /users/:id` already established that textual silence isn't the ceiling (D-15's verb-agnostic "every command" applies regardless of which specific `contracts/*.md` file happens to restate it) is a real inconsistency in this plan's own reasoning, not a factual distinction between the two routes.

**Decision**: apply `RequireIdempotencyKeyGuard` to `PATCH /me/photo` too, for the same reason `PATCH /users/:id` got it. This revisits the multipart-body-hashing question `POST /files/avatars` (decision #1) already worked through: `IdempotencyInterceptor.hashRequest()` reads `request.body`, which is deterministically absent for every multipart request regardless of actual file bytes (multer hasn't run yet at that point in the pipeline) — so a same-key retry still correctly replays the stored response (the behavior that actually matters), and the only degraded case is a key mistakenly reused across two *different* uploads, which silently replays the first response rather than 409ing — not a security issue, and `uploadAvatar()`'s own `sha256` dedupe already makes that scenario low-stakes, exactly as already accepted for `POST /files/avatars`. Applying the identical guard to an identical hazard with an identical mitigation, rather than treating the hazard as acceptable in one place and disqualifying in another, is the consistent position.

**7. `reset-password`/`change-password` DO require `Idempotency-Key`** — `contracts/auth.md` names both explicitly in its blanket sentence. `RequireIdempotencyKeyGuard` applies to both, reused as-is (created by User Story 1, already reused by User Story 3, and reused again here on two more routes). `forgot-password`/`verify-otp` are deliberately NOT given one — neither is named in that sentence, and both already have their own purpose-built anti-abuse mechanism (the 30-second resend cooldown; the 5-attempt cap) that an `Idempotency-Key` would add nothing to.

**8. `ThrottlerGuard` stays unapplied to these four new `/auth/*` routes, same as every route already on `AuthController`.** `throttler.config.ts`'s `isAuthRoute()` already matches any `/auth/*` path generically, so the 10-req/min-per-IP `auth` throttler config is *ready* for these routes the moment `ThrottlerGuard` is ever actually applied anywhere — but it still isn't, by every work unit since WU-04's own design note ("ready for a later work unit to apply... once there are live routes to rate-limit"), and nothing in `tasks.md`'s T062-T070 asks this story to be that later work unit. Noted explicitly here rather than silently inherited, so a reviewer doesn't have to independently rediscover that this is a known, pre-existing, deliberate deferral and not an oversight unique to this story.

**9. "Revokes every other active session" (FR-014) is, in this codebase's actual mechanism, revoking literally every session, including the one that just authenticated the request** — `tokenVersion` bump invalidates every outstanding access token indiscriminately (`ActiveAccountGuard`, WU-04), and there's no per-session exemption mechanism to spare "this one." `tasks.md`'s own T069 already expects this for `change-password` ("on success routing back to Sign in (since other sessions — including, potentially, this one's refresh token — were just revoked)") — this story applies the identical behavior to `reset-password` too (the user is by definition *not* currently signed in when resetting a forgotten password, so there's no "this session" to even distinguish there). **Decision**: a shared `AuthService` helper bumps `User.tokenVersion` (`{ increment: 1 }`, same idiom `UsersService.update()` already uses for deactivation) and calls a new `TokenService.revokeAllRefreshTokens(userId)` (`updateMany({ where: { userId, revokedAt: null }, data: { revokedAt: new Date() } })`, mirroring `revokeRefreshToken`'s existing shape) — both halves are needed, since the `tokenVersion` bump alone only stops *access* tokens; an unrevoked refresh token could otherwise mint a fresh one with the new `tokenVersion` baked in, silently defeating the whole point.

Two different companies each with a user sharing the same username (e.g. both have an `"admin"`) — a `forgot-password` call carrying one company's `companyCode` must only ever be able to reach and reset *that* company's `"admin"`, confirmed by checking the other company's `"admin"` password is genuinely unchanged afterward (decision #3a — the gap this item exists to close).
11. A `forgot-password`/`verify-otp` call with a `companyCode` that doesn't resolve to any real company → the identical `200 { maskedMobile }` (or identical `OTP_INCORRECT`, for verify-otp) a nonexistent username already gets — never a distinguishable error, confirming decision #3a's "lookup mirrors `login()`, outcome-on-failure does not" split is genuinely implemented, not just documented.

## API Contract (endpoints built in this scope)

Reproduced from `contracts/auth.md` and `contracts/files.md` (already adversarially-designed in the Phase 1 plan — not re-derived here):

### `POST /auth/login` — public
Request: `{ companyCode?: string; username: string; password: string }`. Response `200`: `{ accessToken, refreshToken, user: { id, name, role, companyId, permissions } }`. Errors: `401 INVALID_CREDENTIALS`, `403 ACCOUNT_INACTIVE`, `429 RATE_LIMITED`.

### `POST /auth/refresh` — public (presents a refresh token)
Request: `{ refreshToken: string }`. Response `200`: new token pair. Errors: `TOKEN_EXPIRED`, `409 TOKEN_REUSED`.

### `POST /auth/logout` — any authenticated role
Request: `{ refreshToken: string }`. Response `204`.

### `GET /files/:id?token=&thumb=` — any role holding a valid signed token
Response: image bytes. Errors: `401/403 FORBIDDEN`, `404 NOT_FOUND`.

(`forgot-password`/`verify-otp`/`reset-password`/`change-password`, `/companies`, `/users`, `/me` are User Stories 1–4, out of this T001–T041 scope — they are separate, later work units per `tasks.md`.)

## Security Considerations

- **Trust boundaries**: `/auth/login`, `/auth/refresh` are public (unauthenticated) inputs — every field is untrusted and Zod-validated (WU-04/T026). `/auth/logout` and `/files/:id` require a valid bearer/token.
- **Input validation**: every request body validated against a `packages/shared` Zod schema before reaching a handler (Constitution rule 5).
- **Rate limiting**: `/auth/login` at 10/min/IP plus the 6-failures/15-min per-username lockout (FR-010); general authenticated traffic at 120/min/user (WU-04/T023).
- **AuthN/AuthZ**: `JwtAuthGuard` → `ActiveAccountGuard` → `RolesGuard`/`PermissionsGuard`, in that order, on every non-public route (WU-04).
- **Secrets management**: `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `FILE_URL_SECRET`, `SEED_SYSTEM_ADMIN_PASSWORD` are env-only, Zod-validated at boot (WU-01/T005), never committed; `.gitignore` already covers `.env*` (verify in WU-01).
- **Password/token storage**: passwords argon2id-hashed (WU-05/T031); refresh tokens stored only as an argon2id hash, never the raw opaque value (data-model.md).
- **Tenant isolation**: two independent layers (Prisma extension + Postgres RLS) on every `User`/`FileObject` operation (WU-03), extended to `UserSalaryRate` by User Story 3 (gap #7 — the first story to write to that table) — Constitution rule 2, the project's single highest-stakes rule.

## External Dependencies

- **PostgreSQL 16**: required, local dev instance, `DATABASE_URL`, a **direct connection** (not a transaction/statement-mode pooler) — Architecture §5 warns that `SET LOCAL app.company_id` (WU-03) only holds under a direct connection or a transaction-mode pooler; a statement-mode pooler would silently defeat RLS. This scope only ever runs against a local dev Postgres with a direct connection, so the caveat doesn't bind yet — it becomes relevant again at Railway deployment (out of scope here, and already Railway's own configuration per Architecture §5/§17, not something this plan's code needs to enforce).
- No other credentialed external service is touched in T001–T041 — SMS (OTP), Firebase (push) and Google Maps are not needed until later work units (US4, 015-notifications, 006-shops respectively). No external-service human checkpoint is needed for this scope.
